# Kafka 구조 한 번에 이해하기: 헷갈리는 지점 정리

- 이 문서: 클러스터, 브로커, 토픽, 파티션, 복제본, 세그먼트, offset, 컨슈머 그룹이 **서로 어떻게 연결되는지**. 처음 공부할 때 실제로 헷갈렸던 질문을 따라가며 정리했다.
- 용어 표, 프로듀서·컨슈머 설정, Spring Boot 설정은 [kafka-basics.md](kafka-basics.md). 직접 눈으로 확인하는 실습은 [케이스 00](cases/00-warmup-cli.md).
- 기준 버전: Apache Kafka 4.4(KRaft). ✔ 표시는 로컬 `apache/kafka:4.4.0` 컨테이너에서 `kafka-configs.sh --describe --all` 로 직접 확인한 브로커 기본값(2026-11-27).

## 0. 한 장 요약

```
[물리: 브로커 입장]                         [논리: 앱 입장]

클러스터 (하나)                              토픽 order-events  ← 이름 + 설정(메타데이터)
└─ 브로커 1, 2, 3 (서버)                      ├─ 파티션 0  ← 실제 데이터, offset 0,1,2...
    └─ 파티션 복제본들 (리더 or 팔로워)       ├─ 파티션 1
        └─ 세그먼트 파일들 (.log)             └─ 파티션 2

쓰기: 토픽 + key ─hash─▶ 파티션 번호 ─메타데이터─▶ 그 파티션의 리더 브로커 ─▶ 활성 세그먼트 끝에 추가
읽기: 그룹이 파티션을 배정받음 ─▶ (그룹, 토픽, 파티션)의 커밋 offset ─▶ 리더에서 그 offset 부터 순서대로 poll
```

| 개념 | 한 줄 정의 | 실체 |
|---|---|---|
| 클러스터 | 브로커들의 묶음 | 보통 하나. "클러스터 3개"가 아니라 "브로커 3대" |
| 브로커 | Kafka 서버 한 대 | 직접 띄우는 프로세스. 수는 운영자가 정한다 |
| 컨트롤러 | 클러스터 관리자 | KRaft 쿼럼. 메타데이터, 브로커 상태, 리더 선출 |
| 토픽 | 메시지 종류의 이름 | **메타데이터일 뿐**. 데이터 폴더가 없다 |
| 파티션 | 토픽을 나눈 조각 | 실제 데이터 단위. 순서, offset, 병렬 처리의 단위 |
| 복제본(replica) | 파티션 하나의 사본 | 리더도 복제본이다. 각 브로커 디스크의 폴더 |
| 리더 / 팔로워 | 복제본의 역할 | **파티션마다** 리더 1개, 나머지는 팔로워 |
| 세그먼트 | 복제본을 나눠 저장한 파일 | `.log` + `.index` + `.timeindex` |
| offset | 파티션 안 메시지 번호 | 파티션마다 0 부터 따로 증가 |
| key | 메시지에 앱이 붙이는 값 | **쓸 때** 파티션을 고르는 데만 쓴다 |
| 컨슈머 그룹 | 같은 `group.id` 를 쓰는 컨슈머들 | 논리적 이름. 커밋 offset 을 그룹마다 따로 갖는다 |

## 1. 클러스터, 브로커, 컨트롤러

- **브로커 = Kafka 서버 한 대.** 서버를 3대 띄우면 브로커 3대다. 파티션 수나 토픽 수에 따라 브로커가 생기지 않는다.
- **클러스터 = 브로커들을 묶은 전체.** 브로커들이 "서로 클러스터를 이루는" 것이고, 토픽·파티션·세그먼트가 클러스터를 이루는 게 아니다.
- **컨트롤러**가 클러스터를 관리한다.
  - 토픽, 파티션, 복제본 위치, 리더 같은 메타데이터를 들고 있다.
  - 브로커가 죽었는지 감지하고 새 리더를 뽑는다.
  - Kafka 4.0 부터 ZooKeeper 가 없어지고 KRaft(컨트롤러끼리 Raft 합의)만 지원한다.
  - 이 저장소의 compose 는 노드 하나가 브로커와 컨트롤러를 겸한다(`KAFKA_PROCESS_ROLES: broker,controller`). 자세한 내용은 [kafka-basics.md §14](kafka-basics.md).

## 2. 토픽은 메타데이터, 데이터는 파티션에 있다

- 토픽은 **이름과 설정**이다. "order-events 는 파티션 3개, 복제 3벌, 보존 7일, P0 리더는 브로커 1…" 같은 정보.
- 실제 메시지는 전부 **파티션**에 저장된다. 브로커 디스크를 열면 토픽 폴더는 없고 파티션 폴더만 있다.

```
/var/lib/kafka/data/
├─ order-events-0/      ← 토픽 이름 + 파티션 번호
├─ order-events-1/
├─ payment-events-0/
└─ __consumer_offsets-17/
```

- **토픽 1 : 파티션 N.** 파티션 하나는 딱 한 토픽에만 속한다.
- **파티션 수와 복제 수는 토픽마다 정한다.** 토픽 A 는 파티션 3개, 토픽 B 는 12개처럼 다르게 줄 수 있다.
  - 토픽을 만들 때: CLI `--partitions 6 --replication-factor 3`, Spring `TopicBuilder.name("x").partitions(6).replicas(3)`
  - 브로커 설정(compose)의 `num.partitions`, `default.replication.factor` 는 값을 안 줬을 때 쓰는 **기본값**일 뿐이다.

## 3. 파티션(나누기) vs 복제(복사): 가장 헷갈리는 곳

**같은 토픽이어도 파티션마다 내용이 다르다.** 메시지 하나는 딱 한 파티션에만 들어간다.
**같은 파티션의 복제본끼리만 내용이 같다.**

| | 파티션 (나누기) | 복제 (복사) |
|---|---|---|
| 하는 일 | 토픽의 메시지를 key 기준으로 **쪼개 나눠 담는다** | 파티션 하나를 **똑같이 복사**해 여러 브로커에 둔다 |
| 메시지 하나는 | **한 파티션에만** 들어간다 | 그 파티션의 모든 복제본에 들어간다 |
| 내용 | P0 ≠ P1 ≠ P2 | P1 리더 = P1 팔로워 |
| 목적 | **병렬 처리**(컨슈머가 나눠 읽음), 처리량 | **고가용성**(브로커가 죽어도 데이터 유지) |
| 정하는 값 | `partitions` | `replication.factor` (RF) |

### 브로커 3대, 파티션 3, RF=3

```
                 Broker 1        Broker 2        Broker 3
P0 (order-2,3)   [P0 리더]   =   [P0 팔로워] =   [P0 팔로워]     ← 가로: 같은 파티션 = 같은 내용
P1 (order-1)     [P1 팔로워] =   [P1 리더]   =   [P1 팔로워]
P2 (그 밖)       [P2 팔로워] =   [P2 팔로워] =   [P2 리더]
                    ↕ 다름          ↕ 다름          ↕ 다름        ← 세로: 한 브로커 안 = 서로 다른 조각
```

- **가로(같은 파티션 번호) = 같은 내용** → 복제, 고가용성
- **세로(같은 브로커) = 다른 내용** → 나누기, 부하 분산
- 복제본은 9개지만 **내용은 3종류**(P0, P1, P2)다. "파티션 9개"가 아니라 "파티션 3개, 복제본 9개".
- 브로커 1이 죽어도 P0, P1, P2 모두 브로커 2·3 에 사본이 있다. 그중 하나가 새 리더가 된다.

### 개수 계산

```
전체 복제본 수 = Σ(토픽별 파티션 수 × 토픽별 RF)
```

| 브로커 | 토픽 | 파티션(토픽당) | RF | 파티션 | 복제본 | 브로커 1대당 복제본 |
|---|---|---|---|---|---|---|
| 3 | 1 | 3 | 3 | 3 | 9 | 3 (리더 1) |
| 3 | 1 | 6 | 3 | 6 | 18 | 6 (리더 2) |
| 3 | 1 | 3 | 2 | 3 | 6 | 2 |
| 3 | 2 | 3 | 3 | 6 | 18 | 6 (리더 2) |
| 3 | 3 | 3 | 3 | 9 | 27 | 9 (리더 3) |
| 3 | A:3, B:6 | - | 3 | 9 | 9 + 18 = 27 | 9 |
| 5 | 1 | 3 | 3 | 3 | 9 | 5대에 나눠 배치 |
| 1 (이 저장소) | 1 | 3 | 1 | 3 | 3 | 3 (전부 리더) |

- 복제본 수를 정하는 건 **RF** 다. 브로커 수는 "RF 를 최대 얼마까지 줄 수 있나"와 "몇 대에 나눠 담나"만 정한다.
- 리더가 정확히 위 표처럼 나뉘는 건 아니다. Kafka 가 고르게 나누려고 할 뿐이다.

### RF ≤ 브로커 수 (무조건)

- 같은 파티션의 복제본 두 개를 한 브로커에 두면 그 브로커가 죽을 때 둘 다 사라진다. 그래서 **같은 파티션의 복제본은 반드시 서로 다른 브로커**에 둔다.
- 브로커 3대에 RF=4 로 토픽을 만들면 `InvalidReplicationFactorException` 으로 **생성이 거부된다.**
- 검사는 **만들 때** 한다. 만든 뒤 브로커가 줄면 토픽은 남고 복제본이 모자란 상태(under-replicated)가 된다. → §4

### 파티션이 많을수록 좋은가

- 복제본 하나하나가 디스크 폴더, 열린 파일, 복제 트래픽, 리더 선출 대상이다. 무작정 늘리면 브로커 부담이 커진다.
- 파티션은 **늘릴 수는 있어도 줄일 수 없다.** 늘리면 `hash(key) % 파티션 수` 결과가 바뀌어 같은 key 가 다른 파티션으로 가므로 순서가 잠깐 깨질 수 있다.
- 기준: "컨슈머를 최대 몇 대까지 늘릴까". 한 그룹에서 동시에 일하는 컨슈머는 **파티션 수까지만** 늘어난다.

## 4. 리더, 팔로워, ISR, 리더 선출

- **리더는 토픽당 하나가 아니라 파티션당 하나.** 파티션 3개 토픽이면 리더 3개가 여러 브로커에 흩어져 있다. 그래서 읽기·쓰기 부하가 나뉜다.
- 리더도 복제본이다. `replication.factor=3` 은 "원본 1 + 사본 3"이 아니라 **리더 포함 총 3벌**.
- 프로듀서와 컨슈머는 기본적으로 **리더와만** 통신한다. 팔로워는 리더에게서 가져와(fetch) 복제만 한다.
  - 설정하면 컨슈머가 가까운 팔로워에서 읽게 할 수도 있다(`replica.selector.class`, rack 인식). 기본은 리더.

```
kafka-topics.sh --describe --topic order-events
Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
Partition: 2  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2
```

- `Replicas`: 복제본이 있는 브로커 목록. **첫 번째가 선호 리더(preferred leader)**
- `Isr` (In-Sync Replicas): 리더를 충분히 따라잡은 복제본. 일정 시간(`replica.lag.time.max.ms` = 30초 ✔) 안에 따라잡지 못하면 ISR 에서 빠진다.

### 리더는 자동으로 정해진다

1. **토픽 생성 시**: Kafka 가 복제본 위치를 정하고 리더가 브로커들에 고르게 나뉘도록 배치한다.
2. **리더 브로커가 죽으면**: 컨트롤러가 그 브로커가 리더였던 파티션마다 **ISR 중 하나**를 새 리더로 뽑는다. 메타데이터가 바뀌고, 프로듀서·컨슈머는 에러를 받으면 메타데이터를 다시 읽어 새 리더로 자동으로 붙는다. 앱 코드는 할 일이 없다.
3. **죽었던 브로커가 돌아오면**: 리더를 따라잡아 ISR 에 다시 들어간다. 주기적으로(`leader.imbalance.check.interval.seconds` = 300 ✔) 리더가 선호 리더에서 벗어난 게 많으면 되돌린다(`auto.leader.rebalance.enable` = true ✔).
4. **직접 조절**(운영자 작업, 드묾)
   - 리더만 지금 선호 리더로 되돌리기: `kafka-leader-election.sh`
   - 브로커를 추가했거나 한쪽에 몰렸을 때 복제본 위치 자체를 옮기기: `kafka-reassign-partitions.sh`

### 유실 없는 쓰기: acks, min.insync.replicas, unclean 선출

- `acks=all`(프로듀서 기본값): ISR 전부에 기록돼야 성공 응답.
- `min.insync.replicas`: 쓰기를 받기 위한 최소 ISR 수. **기본 1 ✔** 이라 운영에서는 올려야 한다.
- `unclean.leader.election.enable` = **false ✔**: ISR 밖의 뒤처진 복제본은 리더가 될 수 없다. 따라잡지 못한 메시지가 유실되기 때문.

| 브로커 3, RF=3, min.isr=2, acks=all | 결과 |
|---|---|
| 3대 정상 | 쓰기 OK |
| 1대 장애·점검 | ISR 2 ≥ 2 → **쓰기 OK, 유실 없음** |
| 2대 장애 | ISR 1 < 2 → 쓰기 거부(`NotEnoughReplicasException`). 유실 대신 멈춤 |

### 보통 이렇게 설정한다 (운영)

| 항목 | 흔한 값 | Kafka 기본값 |
|---|---|---|
| 브로커 수 | 3대 이상 | - |
| `default.replication.factor` / 토픽 RF | 3 | **1 ✔** |
| `min.insync.replicas` | 2 | **1 ✔** |
| 프로듀서 `acks` | all | all |
| 파티션 수 | 처리량·컨슈머 수 기준. 3, 6, 12 처럼 | `num.partitions` **1 ✔** (이 저장소 compose 는 3) |
| `auto.create.topics.enable` | false (오타 토픽 자동 생성 방지) | **true ✔** |

## 5. 세그먼트와 offset

- **offset = 메시지 하나하나의 번호.** 파티션 안에서 들어온 순서대로 0, 1, 2 … 붙는다. 파티션마다 따로 센다.
- **세그먼트 = 그 메시지들을 담은 파일 조각.** 파티션(정확히는 각 복제본)을 큰 파일 하나 대신 여러 파일로 나눠 저장한다.
- 세그먼트 **안에** 메시지들이 쌓이고, 메시지마다 offset 이 붙어 있다. 세그먼트에 "로그 파일들"이 쌓이는 게 아니라 **세그먼트 자체가 로그 파일**이다.

```
order-events-1/                         ← 파티션 1 의 복제본 하나(브로커 디스크의 폴더)
├─ 00000000000000000000.log            ← 세그먼트: offset 0 ~ 9999 메시지
├─ 00000000000000000000.index          ←   offset → 파일 위치 찾기용
├─ 00000000000000000000.timeindex      ←   시간 → offset 찾기용
├─ 00000000000000010000.log            ← 세그먼트: offset 10000 ~ 19999
├─ ...
└─ 00000000000000020000.log            ← 활성 세그먼트: 지금 여기 끝에만 추가
   (파일 이름 = 그 세그먼트 첫 메시지의 offset)
```

| | offset | 세그먼트 |
|---|---|---|
| 무엇 | 메시지 번호 | 메시지 여러 개를 담은 파일 |
| 범위 | 파티션 전체에서 이어짐. 세그먼트가 바뀌어도 0 부터 다시 세지 않음 | 일정 크기·시간마다 새 파일 |
| 누가 신경 쓰나 | 개발자, 컨슈머 | 브로커 내부 |

- 책에 비유하면 **offset = 쪽 번호, 세그먼트 = 권(1권, 2권 …)**.
- 새 세그먼트로 넘어가는 시점(roll): 크기 `log.segment.bytes` = 1GB ✔ 또는 시간 `log.roll.hours` = 168시간(7일) ✔.
- **쓰기**는 항상 활성 세그먼트 끝에만 한다(append-only). 중간 수정이 없어서 디스크 순차 쓰기가 되고 빠르다.
- **삭제**는 메시지 단위가 아니라 **오래된 세그먼트 파일 통째로** 한다. 보존 기간 `log.retention.hours` = 168시간(7일) ✔ 이 지난 세그먼트를 지운다. 읽었는지 여부와 무관하다.
- **읽기**: 컨슈머가 "offset 10005 줘"라고 하면, 브로커는 파일 이름으로 `10000.log` 를 고르고 `.index` 로 위치를 찾아 거기서부터 보낸다.
- 복제본끼리 세그먼트 **파일을 복사하는 게 아니다.** 팔로워가 리더에게서 메시지를 가져와 자기 세그먼트에 다시 쓴다. 그래서 내용은 같지만 파일 경계는 다를 수 있다.

## 6. 쓰기 흐름: key 가 파티션을 정한다

### key 란

- 앱이 메시지마다 붙이는 값. 보통 **업무 ID**(주문 ID, 회원 ID).
- 앱은 **토픽, key, value** 를 같이 넘긴다. 토픽은 목적지, key 는 "누구 것인지" 표시.

```java
//                 토픽            key              value
kafkaTemplate.send("order-events", order.getId(),  orderJson);
```

- key 는 선택이다. 안 주면 null.
- key 를 쓰는 이유: **같은 주문의 이벤트(생성 → 결제 → 배송)가 같은 파티션에 들어가 순서가 지켜지게.**

### 보내는 순서

```
send("order-events", key="order-1", value)
 ① 메타데이터 확인 : order-events 는 파티션 3개. P0 리더=브로커1, P1 리더=브로커2, P2 리더=브로커3
 ② 파티션 결정     : hash("order-1") % 3 = 1  → P1           ← 프로듀서(클라이언트)가 직접 계산
 ③ 리더 찾기       : P1 의 리더 = 브로커 2                      ← 메타데이터
 ④ 전송            : 브로커 2 로 보냄 (배치로 모아서)
 ⑤ 리더            : P1 활성 세그먼트 끝에 추가, 다음 offset 부여
 ⑥ 팔로워          : 리더에서 가져가 복제
 ⑦ 응답            : acks=all 이면 ISR 전부 복제 후 성공
```

- **hash 하는 건 토픽이 아니라 key.** 토픽은 "파티션이 몇 개고 리더가 어디냐"를 알려 주는 메타데이터로만 쓰인다.
- key 가 정하는 건 **파티션 번호까지**. 리더는 그 파티션의 복제본 중 하나이고 장애 때 바뀔 수 있다. 리더가 바뀌어도 order-1 은 계속 P1 이고, 가는 브로커만 달라진다. 그래서 "key 로 리더 파티션이 정해진다"보다 **"key 로 파티션이 정해지고, 그 파티션의 리더에게 보낸다"** 가 정확하다.
- **여러 key 가 한 파티션을 나눠 쓴다.** key 는 수만 개, 파티션은 몇 개뿐이다. 보장되는 건 "같은 key → 항상 같은 파티션" 하나다.

```
order-1, order-4, order-7 ... → P1
order-2, order-5 ...          → P0
order-3, order-6 ...          → P2
```

- **key 가 없으면** 메시지마다 돌아가며 넣지 않는다. 배치 단위로 한 파티션에 몰아 넣고, 배치가 바뀌면 다른 파티션으로 간다(sticky partitioner). 케이스 00 에서 key 없는 `click-*` 3개가 한 파티션에 몰렸다.
- 메타데이터는 프로듀서가 처음 뜰 때 `bootstrap-servers` 의 아무 브로커에게서 받아 캐시한다. 모든 브로커가 메타데이터를 알고 있어서 어디에 물어도 된다.
- 프로듀서는 **커밋 offset 과 무관하다.** 항상 파티션 맨 끝에 붙인다.

## 7. 읽기 흐름: 그룹, 배정, offset 커밋

### Kafka 는 push 하지 않는다. 컨슈머가 pull 한다

- 브로커가 구독자에게 보내 주지 않는다. 컨슈머가 `poll()` 로 **리더 브로커에게** "P1 의 offset 42 부터 줘" 하고 가져간다.
- 읽어도 지워지지 않는다(큐가 아니라 **로그**). 삭제는 보존 기간이 지나야.
- 그래서 여러 그룹이 같은 데이터를 각자 읽을 수 있고, offset 을 되돌려 다시 읽을 수 있고, 느린 컨슈머가 브로커를 막지 않는다. RabbitMQ 는 반대(브로커가 push, 처리 완료하면 삭제). → [kafka-basics.md §8](kafka-basics.md)

### 읽는 순서

```
 ① 컨슈머가 group.id 로 그룹에 참여 → 그룹 코디네이터가 파티션 배정 ("너는 P0, P1 담당")
 ② 코디네이터에게 커밋 offset 조회 → "g1 의 P1 은 5"
 ③ 메타데이터로 P1 리더 찾기 → 브로커 2
 ④ 브로커 2 에 "P1 offset 5 부터" poll → 리더가 세그먼트에서 찾아 메시지 묶음(레코드 배치)을 줌
 ⑤ 처리
 ⑥ 커밋: "g1 은 P1 을 다음엔 6 부터" → 코디네이터가 __consumer_offsets 에 기록
 ⑦ 다음 poll 은 메모리에 있는 위치(6)부터 이어서
```

- 리더는 **세그먼트를 통째로 주지 않는다.** 요청한 offset 부터의 **메시지들**을 준다.
- 컨슈머는 모든 ISR 에 복제가 끝난 위치(High Watermark)까지만 읽는다. 리더에만 있고 아직 복제 안 된 메시지는 안 보인다.

### 컨슈머는 key 를 보지 않는다

- 읽는 기준은 **파티션 + offset** 뿐이다. Kafka 에는 key 로 검색하는 기능이 없다(DB 의 `WHERE key = ?` 같은 건 없다).
- 그룹은 배정받은 파티션의 메시지를 **key 와 상관없이 offset 순서대로 전부** 읽는다.

```
P1 : [0 order-1][1 order-4][2 order-1][3 order-7][4 order-4]
       ▲ g1 은 0, 1, 2, 3, 4 순서로 전부 받는다
```

- key 는 메시지에 같이 실려 와서 앱 코드가 `record.key()` 로 꺼내 쓸 수 있을 뿐이다. 특정 key 만 필요하면 받은 뒤 코드에서 거르거나, 그 용도의 토픽을 따로 만든다.
- **offset 은 key 마다가 아니라 파티션마다 하나의 줄**이다. 위에서 order-1 과 order-4 는 같은 P1 의 offset 줄을 나눠 쓰고, 커밋도 "g1 의 P1 = 5" 하나뿐이다.

### offset 은 어디서 관리하나: __consumer_offsets 와 그룹 코디네이터

- 커밋 offset 은 **(그룹, 토픽, 파티션)** 조합마다 하나다.

```
(g1, order-events, 0) → 3
(g1, order-events, 1) → 5
(g1, order-events, 2) → 0
(g2, order-events, 0) → 1
```

- 저장 위치는 Kafka 내부 토픽 **`__consumer_offsets`**. 세그먼트(원본 메시지)에는 아무것도 기록하지 않는다. 그래서 원본은 그대로이고 여러 그룹이 각자 읽을 수 있다.
  - 파티션 기본 50개 ✔ (`offsets.topic.num.partitions`)
  - compact 토픽이라 key(그룹·토픽·파티션)별 마지막 값만 남는다.
  - 일반 토픽처럼 복제된다. 이 저장소는 브로커가 1대라 compose 에서 `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1` 로 낮춰 뒀다.
- 관리 담당은 **그룹 코디네이터** 브로커.
  - 그룹마다 하나: `hash(group.id) % 50` → `__consumer_offsets` 의 파티션 → **그 파티션의 리더 브로커가 코디네이터**.
  - 하는 일: 멤버 관리(참여·이탈·heartbeat), 파티션 배정과 리밸런싱, 커밋 기록, 시작할 때 커밋 위치 알려 주기.
- 커밋 값은 **"다음에 읽을 offset"** 이다. offset 4 까지 처리했으면 5 를 커밋한다.
- **커밋해도 메시지는 지워지지 않는다.** 그룹의 "읽은 위치 기록"일 뿐.
- 그룹이 빈 채로 `offsets.retention.minutes` = 10080분(7일) ✔ 이 지나면 커밋 기록이 지워진다. 그 뒤에 다시 붙으면 새 그룹처럼 `auto.offset.reset`(earliest / latest)을 따른다.
- 예전 Kafka(0.9 이전)는 ZooKeeper 에 저장했다. 지금은 내부 토픽만 쓴다.

### 실행 중 위치 vs 커밋 위치

- 컨슈머는 실행 중에는 자기 위치를 **메모리**로 기억하며 계속 다음 것을 읽는다.
- 커밋된 offset 을 다시 쓰는 건 **재시작하거나, 리밸런싱으로 파티션이 다른 컨슈머에게 넘어갈 때**다.
- 그래서 **처리는 했는데 커밋 전에 죽으면** 다음 컨슈머가 커밋 위치부터 다시 읽어 **중복**이 생긴다. → 케이스 01, 09

### 순서는 파티션 안에서만

- 각 파티션 안에서는 offset 순서 = 들어온 순서 = 읽는 순서.
- 토픽 전체로는 하나의 순서가 없다. P0 의 offset 3 과 P1 의 offset 5 중 어느 게 먼저 들어왔는지 보장하지 않는다.
- 그래서 순서가 필요한 데이터는 **같은 key** 로 보내 같은 파티션에 넣는다. → 케이스 08

## 8. 컨슈머 그룹 설계와 멱등 처리

### 그룹은 "누가 무슨 일을 하나"로 나눈다

```
토픽 order-events (주문 생성됨)
 ├─ 그룹 inventory-service    → 재고 차감        (서버 3대 = 같은 그룹, 파티션을 나눠 맡음)
 ├─ 그룹 notification-service → 주문 확인 메일
 └─ 그룹 analytics-service    → 통계 적재
```

- 그룹은 실체가 있는 서버가 아니라 **`group.id` 라는 이름**이다. Kafka 는 그룹에 대해 멤버·배정(코디네이터 메모리)과 커밋 offset(`__consumer_offsets`)만 관리한다.
- 그룹은 토픽을 **구독**한다. 한 그룹이 여러 토픽을, 한 토픽을 여러 그룹이 구독할 수 있다. 토픽에 그룹이 고정으로 매핑되는 게 아니다.
- **다른 그룹** = 같은 메시지를 각자 전부 받는다. 하는 일이 달라서 중복이 아니다. 주문 서비스는 이벤트를 한 번만 발행하면 된다(Kafka 를 쓰는 큰 이유).
- **같은 서비스 여러 대** = 같은 그룹. 그룹 안에서는 파티션 하나를 컨슈머 하나만 맡는다 → 메시지 하나는 한 대만 처리.
  - 컨슈머 수 > 파티션 수면 남는 컨슈머는 논다.
  - Spring: `@KafkaListener(groupId = "inventory-service")` 또는 `spring.kafka.consumer.group-id`
- **흔한 실수**: 인스턴스마다 그룹 ID 를 다르게(호스트명 붙이기 등) 주면 3대가 각자 전부 받아 **재고가 세 번 차감**된다. 이건 진짜 중복이다.

### 그래도 멱등은 필요하다: 같은 그룹 안의 재전달 때문

Kafka 기본 보장은 **at-least-once(최소 한 번)**. 같은 그룹 안에서도 같은 메시지가 다시 온다.

| 원인 | 케이스 |
|---|---|
| 처리 후 커밋 전에 죽음 → 재시작 시 다시 옴 | 01 |
| 처리 중 리밸런싱 → 다른 컨슈머가 다시 처리 | 09 |
| 아웃박스 relay 가 발행 후 표시 전에 죽음 → 다시 발행 | 05 |
| 운영자가 offset 을 되돌림(재처리) | 00 7단계 |

그래서 실무 표준은 **at-least-once + 멱등 컨슈머**.

| 방법 | 방식 |
|---|---|
| 처리 기록 테이블 | 메시지 ID 를 `processed_message` 에 **업무 변경과 같은 트랜잭션**으로 INSERT. PK 충돌이면 건너뜀 → 케이스 06 |
| 업무 키 유니크 | `order_id` PK·유니크로 두 번째 INSERT 실패 |
| 조건부 UPDATE | `UPDATE ... SET status='PAID' WHERE id=? AND status='CREATED'` → 이미 바뀌었으면 0건 |
| 덮어쓰기 연산 | "재고를 10 으로 설정"은 멱등, "10 빼기"는 멱등 아님 |

자세한 패턴은 [concepts.md](concepts.md) §1, §3.

## 9. 자주 헷갈린 것: 오해 → 실제

| 오해 | 실제 |
|---|---|
| 브로커 안에 토픽이 있다 | 토픽은 이름표. 브로커 안에는 **여러 토픽의 파티션 복제본**이 섞여 있다 |
| 토픽 데이터가 따로 저장된다 | 토픽 폴더는 없다. 데이터는 전부 파티션 폴더에 |
| 토픽 = 파티션 | 토픽 1 : 파티션 N. 파티션은 한 토픽에만 속한다 |
| 파티션 수는 클러스터마다 정한다 | **토픽마다** 정한다. 브로커 설정은 기본값일 뿐 |
| 파티션 3개면 브로커 3대가 생긴다 | 브로커는 직접 띄우는 서버. 파티션은 기존 브로커에 나눠 배치된다 |
| 같은 토픽이면 파티션마다 내용이 같다 | **파티션마다 다르다**(나누기). 같은 파티션의 **복제본끼리만** 같다(복사) |
| 브로커 하나에 있는 파티션 3개는 내용이 같다 | 서로 다른 조각(P0, P1, P2)이다 |
| 파티션 3 × RF 3 = 파티션 9개 | 파티션 3개, **복제본** 9개. 내용은 3종류 |
| 리더는 별도의 사본이다 | 복제본 중 하나가 리더. RF=3 은 리더 포함 3벌 |
| 리더는 토픽당 하나 / 브로커당 하나 | **파티션당 하나**. 한 브로커가 리더를 여러 개 갖거나 하나도 없을 수 있다 |
| RF 는 브로커 수보다 커도 된다 | **RF ≤ 브로커 수**. 넘으면 토픽 생성 거부 |
| 세그먼트가 여러 파티션에 분산된다 | 세그먼트는 **한 파티션(복제본)의 파일**. 복제는 파티션 단위 |
| 세그먼트 안에 로그 파일들이 쌓인다 | **세그먼트 자체가 로그 파일**. 그 안에 메시지가 쌓인다 |
| 세그먼트 순서 = offset | offset 은 메시지 번호, 세그먼트는 메시지 묶음 파일(쪽 번호 vs 권) |
| 토픽을 hash 해서 파티션을 찾는다 | **key** 를 hash 한다 |
| key 마다 파티션이 따로 있다 | key 가 파티션을 **고른다**. 여러 key 가 한 파티션을 나눠 쓴다 |
| 구독자에게 Kafka 가 보낸다(push) | 컨슈머가 리더에서 **가져간다(pull)** |
| 컨슈머는 key 로 메시지를 찾는다 | key 검색 기능은 없다. **파티션 + offset** 으로 순서대로 읽는다 |
| offset 은 key 마다 / 토픽마다 관리된다 | **(그룹, 토픽, 파티션)마다** 하나 |
| 커밋은 세그먼트에 기록된다 | `__consumer_offsets` 내부 토픽에 기록. 원본은 그대로 |
| 커밋하면 메시지가 지워진다 | 지워지지 않는다. 보존 기간이 지나야 세그먼트째 삭제 |
| 프로듀서는 커밋된 다음 offset 에 쓴다 | 프로듀서는 커밋과 무관. 항상 파티션 끝에 붙인다 |
| 리더가 세그먼트를 준다 | 요청한 offset 부터의 **메시지들**을 준다 |
| 그룹을 나누면 DB 중복 처리가 된다 | 그룹마다 하는 일이 달라 중복이 아니다. 중복은 **같은 그룹 안의 재전달**에서 생기고, 그래서 멱등 처리가 필요하다 |
